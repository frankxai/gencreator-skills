# Review and learn

## Inputs and work
Require the commission/acceptance brief, exact artifact revision, sources/rights, actual checks and founder feedback. Give an independent reviewer the artifact and brief without creator rationale or suspected defects. Use a fresh context when supported; otherwise label self-review. A role name is not delegation evidence. Preserve separate second-provider gates when required and unavailable.

Inspect the actual artifact in its medium and execute the beneficiary's main task. Verify source/claim support, rights, current revision, usability, accessibility, critical states and meaningful outcome. Compare baseline and candidate pairwise with written reasons. Challenge misleading prototype/live, recording/published, lab/field and proposal/approved claims. Include concrete defects with locator, reproduction, consequence and required fix.

Return keep/revise/reject with source-linked findings. Recheck repaired states. Separate deterministic tests from actual model/tool/user evaluations. Recommend a workflow or taste change only with its evidence, scope, disconfirming condition and acceptance owner. Promote a reusable component after demonstrated reuse; promote a taste standard only on accepted founder evidence. Preserve rejected examples and negative results.

## Output and acceptance
Return review identity/context, inspected revision, exercised task, findings, verdict, pending evidence, learning proposal and promotion state. Link each learning to source and artifact. A `keep` verdict does not imply deployment, approval to publish, measured impact or installed runtime behavior.

Pass example: reviewer opens the actual preview, identifies a keyboard focus defect, verifies the repair and retains both versions with a narrow learning proposal. Fail example: creator self-rating called independent validation, a package hash called runtime testing, or an unaccepted preference written into brand canon.

## Failure and boundaries
Missing artifact/source prevents acceptance; review the inspectable scope and name the gap. Stale revision invalidates the review and downstream acceptance. Unknown costs/results remain unknown. Stop after the bounded critic/repair rounds and return unresolved material defects. Do not rewrite existing recurring routines or release the artifact without their separate mandate.

Read [commission contract](../reference-to-commission/references/commission-contract.md) before changing state. Load [tool routing](../reference-to-commission/references/tool-routing.md) only when a connected surface is needed. Reuse the same commission ID and compare the current revision immediately before every dependent action. Keep technical validation, source rights, founder selection and release state separate.

When supplied by the private account package, read `references/private-guidance.md` from the plugin root for approved task-scoped source projections. Its approval/freshness states remain authoritative; a missing projection is a named gap.
